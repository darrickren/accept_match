# Local backend guide

AcceptMatch includes a FastAPI service backed by DynamoDB Local and a local filesystem image store. The safest and
fully tested mode is `APP_MODE=mock`. It uses the same service, repository, schemas, routes, and decision rules as
the optional provider modes without sending data to a model endpoint.

All catalogue records, orders, returns, photos, credentials, and outcomes used by this guide are synthetic.

## Local setup

Python 3.12 and Java 17 or later are recommended.

```bash
python3.12 -m venv .venv-backend
.venv-backend/bin/pip install -r requirements-backend.txt
.venv-backend/bin/python -m backend.scripts.dev secrets
```

Download DynamoDB Local from the official AWS documentation, verify the checksum published by AWS, and extract the
archive into `.local/dynamodb-local/`. The `.local/` directory is ignored by Git.

Start each long-running process in its own terminal:

```bash
.venv-backend/bin/python -m backend.scripts.dev ddb
.venv-backend/bin/python -m backend.scripts.dev seed
.venv-backend/bin/python -m backend.scripts.dev api --mode mock
.venv-backend/bin/python -m backend.scripts.dev frontend
```

The API runs on `http://127.0.0.1:8000` and exposes local OpenAPI documentation at `/docs`. The frontend helper runs
the Streamlit site on `http://127.0.0.1:8501` with `ACCEPTMATCH_AGENT=api` and local demo credentials.

## Implemented routes

- `GET /health`
- `POST /api/demo-auth/login`
- `POST /api/sessions` and `POST /api/sessions/{session_id}/messages`
- `GET /api/items` and `GET /api/items/{item_id}`
- `POST /api/items/{item_id}/acceptance` and `POST /api/checkout`
- `POST /api/uploads`
- `POST /api/returns`, evaluation, status, and additional-evidence routes
- Demo-only admin inventory routes for simulated receipt and inspection

Pydantic request and response schemas, size limits, idempotency keys, optimistic versions, role checks, and stable
error envelopes sit at the API boundary.

## Modes and evidence level

| `APP_MODE` | Behavior | Publication status |
| --- | --- | --- |
| `mock` | Scripted shopping and simulated image findings | Fully offline-tested and the default |
| `gemini-local` | Strands orchestration through the Gemini adapter | HTTP protocol and orchestration tested with mocks; live inference unverified |
| `bedrock-local` | The same orchestration through Bedrock Converse | Scripted and SDK-stub coverage; live inference unverified |
| `agentcore` | Shopping messages invoke a configured AgentCore runtime; returns stay on the mock | Client/runtime contracts tested offline; live inference unverified |

There is no automatic fallback between modes. Provider failures return an explicit API error and do not mutate
state. Commands that can contact Gemini or Bedrock require an explicit approval flag; do not use those commands as
part of offline validation.

## Agent and guardrail boundary

The model-facing layer can interpret free text, select the next question, and produce a structured plan. Read-only
tools expose only the data needed for a turn. Deterministic services retain authority over:

- catalogue identity, availability, version, price, and exact condition evidence;
- accepted defects, required components, and match verification;
- order ownership, return eligibility, photo coverage, and decision status;
- checkout, inventory mutation, simulated warehouse actions, and idempotency.

Structured output is validated with Pydantic. One bounded repair is allowed for invalid model output. The backend
then re-checks referenced item IDs and reconstructs customer-visible cards from local storage.

## Local configuration

Copy `.env.example` to `.env` only if environment-based configuration is convenient. `.env`, `.local/`, provider
state, virtual environments, and Streamlit secrets are ignored. The committed example contains placeholders and
keeps `APP_MODE=mock`.

Important variables include:

| Variable | Default | Notes |
| --- | --- | --- |
| `APP_MODE` | `mock` | Optional provider modes are listed above. |
| `DDB_ENDPOINT` | `http://localhost:8001` | Non-local hosts are rejected in this build. |
| `ACCEPTMATCH_TABLE` | `acceptmatch_demo` | Local table name. |
| `LOCAL_IMAGE_ROOT` | `.local/images` | Local seed and upload storage. |
| `DEMO_TOKEN_SECRET` | none | Generated by the local secrets command; at least 32 characters. |
| `DEMO_PASSWORD_CUST_01` and related values | none | Demo-only persona passwords. |
| `FRONTEND_ORIGINS` | none | Wildcards are rejected. |

Provider-specific values are optional and should never be committed. See `docs/AGENTCORE_PUBLIC.md` for the
placeholder-only AgentCore contract.

## Offline validation

```bash
PYTHONDONTWRITEBYTECODE=1 .venv-backend/bin/python -m pytest tests/backend -q -p no:cacheprovider
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest tests/e2e -q -p no:cacheprovider
```

The backend suite starts DynamoDB Local on an ephemeral port and gives each test a fresh table. The end-to-end suite
starts DynamoDB Local and uvicorn, then drives the real Streamlit application. No test invokes a paid cloud service.

## Demo-only scope

The authentication scheme, local persistence, checkout, administration, return decisions, and fulfilment states
are demonstrations. A production deployment would require a real identity provider, durable encrypted storage,
object authorization, lifecycle and deletion controls, abuse protection, monitoring, secrets management, and a
separate security and privacy review.
